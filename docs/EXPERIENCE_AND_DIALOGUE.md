# The Digital Evidence Lab — desktop experience handover

Design proposal for review • 30 October 2026

## Scope and authority

This handover completes the proposed desktop flow, Amina's conversations, the focused FTK copying sequence, interaction rules, and the screen-reference brief. It is a design specification, not a working software build.

Source: [CSC 1105 Simulation — The Digital Evidence Lab](https://chatgpt.com/library?file_id=libfile_8012ef28c1748191bb8ec678d1ce6df5&account_id=personal), storyboard draft v1.0. The original learning objectives, evidence, technical comparisons, assessment weights and correction opportunities remain authoritative. Windows, Google applications, software choices, filenames, chat wording and timing below are proposed delivery adaptations. The name Alex and plate KDA 417Q in the visual references are synthetic placeholders.

**Approved visual constraint:** the PC displays Windows wallpaper and application windows. Never put a laboratory photograph, office render, desk, monitor bezel or room behind its desktop. The physical workstation is a separate 3D environment supplied by the user. Amina may have a natural background inside her Meet video tile; the evidence photograph is viewed inside its application.

## Experience in one sentence

The learner powers on a workstation, signs in, receives a case from Amina, personally opens each application and its files, prepares verified text/image/audio outputs, submits them through Chat, and completes a handover within a 200 MB processing allocation.

## One continuous computer

- Use a persistent Windows desktop, taskbar, Start menu, File Explorer, browser and native-style application windows. Minimise, restore and switch windows without losing work.
- Opening is always learner initiated: desktop shortcut, taskbar item, Start menu result or explicit link click. Approval never launches a program.
- A clicked Drive link may open its destination normally in the browser. That is a user action, not automatic navigation.
- Applications open to an empty workspace or their remembered state. Use File > Open, an equivalent Open action, or supported drag-and-drop to load files. Do not preload the next assignment silently.
- Saving uses a familiar file dialog with a sensible suggested filename and folder. The learner confirms Save or Export.
- Submitting uses Chat's attachment control, a file picker, then Send. Saving alone is not submission.
- Intake records are available at the beginning; later permissions release working assets and assignments. Apps can remain installed and launchable. This is more plausible than repeatedly installing or granting use of locally installed programs.
- A locked assignment gives a brief reason and returns to the current work. Earlier approved files remain accessible.
- All accounts, permissions, file operations, calls, notifications and transfers happen within the simulation. No real Google credentials or account connection is required.
- No scene numbers in learner-facing UI. Screen IDs in this handover are production references only.

Suggested order: opening → sign-in → Chat → Drive → briefing → intake → physical drive connection → FTK → text → review → image → review → physical tape preparation → audio → review → handover → closing call/debrief. Reference numbering groups related screens and does not impose a different learning order.

The existing MIVA opening and title remain short shell states. Name entry moves to Windows sign-in. Put the required title, learner name, role, case ID, goal, plan, fictional-scenario notice and assessment statement in the briefing's case-summary view. Avoid a second name form or repeating the same spoken briefing.

The only departures from the desktop are power-on, connecting the protected evidence drive, and preparing the microcassette/audio interface. A small user-activated “View equipment” control returns to that 3D workspace when needed. Returning restores the desktop exactly where it was.

## Opening and meeting delivery

The simulated lab clock begins at 09:05 in Nairobi. It is a story clock, not the learner's actual system time. Speed is not assessed.

Use the script's opening narration in the first Meet call, supplemented by its case ID and role details. Amina is a Black Kenyan woman, with a composed Kenyan English voice. Keep one consistent face, voice and wardrobe across both calls. Default captions on; transcript and replay available. No narration overlapping another audio stream.

The invitation appears after the learner has opened the intake folder. It can say “Case 0417 briefing — ready to join.” If a scheduled reminder is shown, make it ready at the next meaningful milestone: never force the learner to wait for a countdown or miss an appointment.

Clicking the invitation opens the familiar Meet pre-join state. Camera off with a learner avatar, microphone muted, captions available. Join now starts the call. No actual camera or microphone permission is needed. Skip ends the briefing audio and leaves the transcript accessible. Leaving a call does not automatically open FTK.

The closing call reuses the same Meet interface and Amina portrait. It introduces the existing debrief, rather than creating another assessed task. The learner clicks the shared handover record to inspect their feedback.

### Audio review

| Validation result | Reply |
|---|---|
| 8 kHz capture | “The buzzer's important high-frequency content is missing. The sampling rate is too low for this task.” |
| 16 kHz capture | “Speech is clearer, but the buzzer is not fully represented. Compare with 44.1 kHz.” |
| 8-bit quantisation | “The low-level speech is harder to distinguish. Compare the quantisation depth.” |
| 96 kHz or 24-bit comparison | “That uses more storage without a useful improvement in this example. Compare it with 44.1 kHz and 16-bit.” |
| MP3 master | “Keep a lossless master. MP3 discards information and can only serve as a separate listening copy here.” |
| Upsampled low-quality capture | “A higher export setting cannot restore information lost during capture. Revisit the capture comparison.” |
| Above 100 MB | “This exceeds the audio allocation. Review the settings while keeping the speech and buzzer.” |
| Pass | “The lossless master preserves the required speech and buzzer, within the allocation.” |

Then:

> All three outputs are ready for your final check. Open the processing record, review each item against its requirement, and confirm the originals remain unchanged.
>
> [Case record: Final handover]

### Handover and closure

**Failed check:** “The [item] check does not match the submitted file. [Specific evidence]. Use Open file to return to it; your other work is saved.”

**Budget exceeded:** “The processing package exceeds 200 MB. Review [largest counted item] and any optional copies without reducing the required quality.”

**Passed:**

> Handover received. The files and processing record agree.
>
> Let's review your decisions together.
>
> [Meet invitation: Case 0417 handover review · Join]

Closing call introduces the four feedback areas and uses the script's closing meaning: text intact, plate legible, buzzer preserved, originals untouched, allocation met. Only claim outcomes that actually passed. The learner opens the record, reviews their own choices and finishes.

## Notifications, pacing and sound

- Toasts last roughly five seconds, then remain in Chat/unread state. No essential instruction disappears permanently.
- One quiet notification sound per new message group. No sound for every typing dot or sentence.
- Amina's typing indicator lasts around 1–2 seconds. It signals authored simulation review, not a real person online. Reduced-motion mode uses a static “Reviewing…” label.
- Evaluate the submitted file version first, then select the correct response. Never approve merely because Send was clicked.
- Do not steal focus, minimise another app, cover a save dialog, or launch the next program on approval. Queue notifications during critical dialogs and audio playback.
- Batch routine approval plus next-task guidance into one notification group.
- No compulsory free-text chat. Optional brief acknowledgements can be sent by the learner; assessed rationale goes into the case record.
- No background music. Optional low computer hum belongs to the physical workspace. Duck incidental sound during Amina's calls and audio comparisons.
- Pause freezes playback, typing, notifications and pending transitions. Resume continues without duplicate messages.
- Idle help is gentle and contextual; do not repeatedly ping while the learner reads. Keep the script's short hints available without forcing timed responses.

## Focused FTK Imager workflow

This is a proposed acquisition wrapper for the script's preservation objective, not a new forensic certification module. Keep system defaults prefilled and preserve native menu/dialog patterns.

1. **Connect safely.** At the bench, connect evidence drive → write-blocker → PC. Show the hardware status. Return to the desktop by the learner's action.
2. **Open FTK Imager.** Double-click its shortcut or select it in Start. The application does not launch just because the cable was connected.
3. **Choose acquisition.** File → Create Disk Image. Select Physical Drive and the explicitly labelled simulated evidence drive. The system drive is recognisable but not a valid source for this case.
4. **Choose destination.** Add an E01 destination. Prefill case KIA/DEL/2026/0417 and examiner name. The learner confirms E:\EvidenceStore\0417\drive.E01. Keep advanced compression/fragment defaults out of the learner's required decisions.
5. **Enable verification and start.** Retain the native “Verify images after they are created” option. Start performs a short visibly simulated acquisition; do not make the learner wait real drive-imaging time.
6. **Read verification.** Show successful/failed verification, bad-sector result, and actual consistent simulated checksum data. The mockup abbreviates the checksum to “Match”; the build must not present invented full hashes as computed values.
7. **Open the resulting image.** Add Evidence Item → Image File, select drive.E01. Browse its contained witness and CCTV files. Use the chosen reference version's native export action to export the two working files to C:\Cases\0417\Working.
8. **Verify working exports.** The case record checks the exported bytes against the preserved files. Store a baseline before representation changes. Amina releases text processing only after this passes.

The source drive and acquisition image are part of the preserved evidence store. The simulated drive contains the digital items, not a digital copy of the still-analogue cassette. Drive intake links are records/previews, not another uncontrolled original. The 200 MB allocation covers the processing outputs and retained working copies; do not incorrectly count an entire physical-drive image against it.

Wrong destination attempts are prevented before a write. A damaged derivative can be recreated from the preserved baseline. Preserve the script's correction log without actually destroying an original or teaching that a damaged physical source can magically be restored.

## Text task: exact content and checks

Canonical UTF-8 fixture, without BOM and without a final newline:

```text
Habari Chébet 👋 Mzigo umefika ✔ Tuma KSh 50,000 → M-Pesa leo 📦 “Usimwambie yeyote” 🤝 — sawa?
```

This exact string has 92 Unicode code points and 112 UTF-8 bytes. Editor wrapping is visual and must not insert newline bytes. JavaScript string.length counts UTF-16 code units; use code-point-aware counting for this fixture.

| Representation | Preserved | Size | Meaning |
|---|---:|---:|---|
| ASCII with unsupported characters replaced by ? | 83/92 | 92 B | Symbols and emoji lost |
| ISO-8859-1 / Latin-1 with replacement | 84/92 | 92 B | Accent retained; other special characters lost |
| UTF-8 without BOM | 92/92 | 112 B | Readable and searchable |
| Screenshot | Visually represented | About 48 KB | Not a searchable text representation |

The custom Case record comparison panel implements these four choices. It is a separate training window, not a fake native Notepad++ menu. Do not equate Windows ANSI with ASCII or Latin-1. In Notepad++, interpreting bytes and converting text to another encoding are separate operations. Begin from correctly interpreted preserved source text; conversion cannot reconstruct question marks after a lossy save.

Required learner path: open working text → compare representations → choose appropriate conversion if needed → Save As → close/reopen → choose correct decoding → verify → attach the saved file in Chat. Pass only when saved UTF-8 bytes decode to the canonical characters and the learner has checked the matching interpretation. Keep the script's two-second stable preview as a debounce, not an extra hold gesture.

## Image task: pixels, colour, resolution and print

Use GIMP's native toolbox, image canvas, layers dock, Colour Picker, Scale Image, Print Size and export workflow. The synthetic photograph should dominate the canvas. The number plate must actually support the stated inspection at native resolution; do not create a tiny unreadable source and generate detail by zooming.

The separate Case record window hosts the teaching-only RGB matching and print comparisons. Keep it collapsible and restore the image canvas when not needed.

1. Open cctv_working.jpg manually.
2. Inspect plate-background, dark-character and sky pixels. Targets approximately (250,210,20), (15,15,15), and (135,190,235). Derive actual displayed readings from the asset; prepare suitable sample regions. Complete the swatch match within ±15 per channel.
3. Compare dimensions using independent derivatives from the preserved baseline. Do not let a low-resolution trial overwrite the only working source.
4. Inspect PPI separately from pixel scaling. Explain the trade-off briefly in the record.
5. Export a derivative, reopen/check it, then attach it in Chat. The source JPEG remains untouched. Proposed final derivative: cctv_working.png; retain original-source identity separately.

| Dimensions | Uncompressed RGB estimate | Script's illustrative plate width | Result |
|---|---:|---:|---|
| 640 × 480 | 0.9216 MB | About 40 px | Unreadable |
| 1280 × 960 | 3.6864 MB | About 80 px | Marginal |
| 4000 × 3000 | 36 MB | About 250 px | Required working resolution |
| 8000 × 6000 | 144 MB | About 500 px | Over budget; no new detail |

Image estimate = width × height × 3 / 1,000,000 MB. This is a teaching/storage-accounting estimate, not the compressed PNG/JPEG file size. Show actual encoded file bytes separately if the build creates real exports. The low-resolution plate widths in the script are approximate; asset geometry and rendered readability should drive the final check.

**Print-size distinction:** 4000 × 3000 at 300 PPI corresponds to 13.33 × 10 inches. A 10 × 7.5 inch print at 300 PPI needs 3000 × 2250 pixels. Do not display all three incompatible values as one native Print Size state. The retained image stays 4000 × 3000 at 300 PPI; the fixed-size print comparison belongs in the lab training panel.

For that separate 10 × 7.5 inch exercise: 72 PPI needs 720 × 540; 150 needs 1500 × 1125; 300 needs 3000 × 2250; 1200 needs 12000 × 9000, exceeding both source detail and budget. Altering PPI metadata alone does not change image pixel count or its uncompressed estimate.

Stage approval requires the source's preferred 4000 × 3000 at 300 PPI, RGB exercise complete, rationale recorded and derivative verification passed. Final handover also checks plate readability and no source-upscaling.

## Audio task: capture once, compare safely

The source remains a sealed analogue microcassette until this assignment. Its intake preview is a record/photo, never an already playable recording.

At the bench, choose Audio Interface & Headphones, load the cassette and connect the player output. Return to the desktop. Open Audacity and select the simulated interface input, mono recording.

Keep three things distinct: the ADC capture setting, Audacity's internal processing sample format, and the export format. Exporting at a higher rate or depth cannot repair an earlier low-fidelity acquisition. The case panel's 8/16/24-bit comparison is an educational ADC demonstration; do not invent unsupported native Audacity controls or mislabel 32-bit float processing as hardware capture depth.

Unlock the teaching controls in order: sampling → quantisation → encoding. Use replayable, level-matched reference previews before tape capture. Preview playback does not advance the original tape or add to its wear count. Once the appropriate settings are confirmed, Record represents a single acquisition with shortened simulation time and a clear indication that ten minutes of source duration are represented. Corrections use reference/baseline simulation data, not repeated physical tape passes.

| Choice | Teaching consequence |
|---|---|
| 8 kHz | Buzzer detail lost; narrow speech bandwidth |
| 16 kHz | Buzzer's upper content missing |
| 44.1 kHz | Preferred sampling rate for the task |
| 96 kHz | Larger data without useful gain in this example |
| 8-bit | Coarse quantisation harms the quiet speech demonstration |
| 16-bit | Preferred depth |
| 24-bit | 50% larger than 16-bit at the same rate; no useful gain here |
| MP3 | Not accepted as the evidence master |
| FLAC or PCM WAV | Accepted lossless representation of the captured samples |

For 600 seconds, mono: PCM bytes = sampling rate × (bits / 8) × 600. 44.1 kHz/16-bit = 52.92 MB. The script estimates FLAC at 55% of PCM, or 29.106 MB. 96 kHz/24-bit = 172.8 MB, exceeding the 100 MB audio allowance. Label FLAC as estimated; actual compression depends on the content. Lossless means the captured digital samples can be recovered exactly, not that every feature of the analogue signal survives digitisation.

The scripted assignment's preferred approval is 44.1 kHz, 16-bit and FLAC or PCM WAV. The broader handover test also tracks minimum capture quality, losslessness and budget. Preserve this distinction rather than pretending 96 kHz is technically incapable of preserving the buzzer.

After capture, File → Export Audio; choose format, filename and Working folder; Export. Reopen/verify the output and attach it through Chat. Saving an Audacity project alone is not a completed audio export.

## Files, submission and final checks

Proposed folders:

```text
E:\EvidenceStore\0417\             preserved acquisition/baselines
C:\Cases\0417\Working\              current text, image and audio derivatives
C:\Cases\0417\Submitted\            versioned submission references
C:\Cases\0417\Reports\              processing log and completion record
```

Avoid counting an attachment as a second physical copy if it is only a reference to an existing object. If revisions or listening/preview copies are retained, count their sizes. If they are discarded, log that action and remove them from the allocation. A submission records immutable file ID/version/settings so a later edit cannot silently change an already approved attachment.

The processing record autofills settings and observations but leaves the required learner judgements unselected. Check text readable/unreadable, image sufficient/insufficient, audio suitable/needs revision, originals unchanged and allocation respected. The rendered reference shows an example after the learner has checked them.

A mismatch explains the specific reason and provides an Open file action. The learner clicks it to return to the relevant application; do not forcibly switch windows. Preserve all other work. Resubmission updates the version and revalidates only affected downstream checks.

**Storage examples:** required outputs using RGB accounting and estimated FLAC total 36 MB + 29.106 MB + 112 B = approximately 65.1 MB before tiny log overhead and any additional retained working copies. The script's optional MP3 listening copy (9.6 MB) and preview (~0.9 MB) bring the example to about 75.5–75.6 MB depending on rounding. Do not show 75.5 MB unless those additional files exist. Original evidence-store objects are excluded; processing masters and retained working copies are included. Compute the actual run total dynamically.

## Review state and assessment

Each assignment tracks: locked → available → editing → saved → submitted → under review → approved or revision requested. Preserve access to approved work. If an approved file is revised, require validation of the new submitted version before final handover. Gate on validated output, not on opening an app or elapsed time.

Record the inspected items, risk order, preservation objective, source protection, working-file identity/version, chosen settings, previews, original comparison, rationale, hints, revisions and review result. Never infer that “originals unchanged” is true solely because the learner checked a box.

Final score = handling × .15 + text × .25 + image × .30 + audio × .30, bounded 0–100. Handling contributions remain split 40% intake/text, 20% image and 40% audio/handover. Speed is not scored; corrections carry no retry penalty. Do not import unrelated XP, badge or attempt-penalty logic from another project.

The source does not fully specify point-level rubrics inside each strand. Do not silently invent deductions or treat the illustrative 100/100 screen as a calculated result. Implement the source-defined checks; any finer rubric requires a separately labelled instructional proposal. Preserve grade bands: 90–100 Senior Evidence Engineer; 75–below 90 Competent; 60–below 75 Developing; below 60 Review and retry.

Debrief has four feedback areas: Preservation, Text, Image, Audio. Each uses the learner's own choice, consequence, reason and expert path. Only one expanded area at a time keeps the screen readable. Optional reflection and lesson-learned note remain unscored. Completion includes learner, skills, actual output settings, storage and Amina's sign-off, with a learning-simulation notice rather than professional certification.

## Visual and interaction specification

- Reference baseline: Windows 11 desktop, modern light Google Chat/Drive, dark Meet call canvas, native Notepad++, FTK Imager, GIMP and Audacity styling. Lock one documented version of each for implementation; mockups are design references, not claims of pixel-exact native screenshots.
- Use requested recognisable product logos and interaction patterns. Do not replace every application's native typography with the project's branding font. The custom case record can use the user's clean sans-serif treatment.
- No simulation HUD, giant floating mentor card, office wallpaper or repeated task cards over the app canvas. Google communication remains in Google windows; custom teaching controls are visibly separate case-record windows.
- Show only essential controls for the learning path while preserving credible menu grouping and window proportions. Unsupported actions provide a brief explanation, never dead buttons without response.
- Use 100dvh layout, readable application scaling and keyboard focus. Keep actual interaction targets at least 44px where needed without making toolbar icons enormous; enlarge hit areas and offer a readable focused view.
- Default-on subtitles at least 18px in the build. Text equivalents for waveform, colour and audio findings. Adjustable demo/call volume. No colour-only pass/fail indicators.
- Keep nonessential animation to 150–250 ms window transitions and subtle notifications. Reduced-motion support. No unexpected camera jumps or auto-switching.
- Tiny development gear remains available across shell, desktop and equipment states for jump/restart/pause/inspect. Keep it out of polished screen references unless reviewing the developer controls.

## Acceptance checks for the future build

1. Start a fresh session; no application opens without a learner action.
2. Save, minimise, switch applications and restore; working state and files persist.
3. Verify that an unread Chat toast can be recovered and a paused timer does not fire in the background.
4. Attempt acquisition without the write-blocker and to the source destination; both are safely prevented.
5. Reproduce the canonical text byte counts, loss and wrong-decoding examples; verify saved bytes rather than a dropdown label.
6. Change only PPI; pixel dimensions and RGB storage remain unchanged. Scale down/up; visible detail and storage behave correctly.
7. Check the exact RGB targets against actual evidence pixels and complete the ±15 swatch activity.
8. Compare audio settings using reference previews; do not replay the physical cassette. Verify capture and export fields separately.
9. Attach a stale/wrong file; Amina requests correction. Attach the verified version; only then does the next assignment unlock.
10. Retain an extra working copy; total allocation increases. Refer to the same object in Chat; it is not double-counted.
11. Fail a handover check; recover the relevant work without a restart or retry penalty.
12. Complete the run using keyboard, captions and text equivalents; verify scores and debrief derive from that run.
